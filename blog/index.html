Devirtualizing Prometheus

A study of the virtual machine · 27 September 2026

Prometheus does not rename your locals and stop. The Vmify step compiles the script into a register machine that shares nothing with Lua bytecode. What you open afterwards is an interpreter, a binary search over block ids, and your program rewritten as assignments to a position register. Strings, numbers, and upvalues are encoded by separate passes that run before or after that compile.

This is a study of that format, and of the order in which it comes back apart. The examples below are the shapes the compiler emits, with registers renamed so the control flow is visible. In a real file those registers are a small reused pool, independent statements inside a block are shuffled, and adjacent assignments are often fused into one multi-assignment. The shuffled order is still a valid order. You do not need the original statement order. You need the edges.

The interpreter

Every compiled function is the same container. It receives the block to start at, the argument table, the upvalue table, and a proxy object whose only job is to stay alive until the call returns. The body is a loop on the position. When the position becomes nil, the loop ends, the position is overwritten with the length of the proxy (that keeps the proxy, and therefore the upvalues, from being collected mid-call), and the return table is unpacked.

local function container(pos, args, upvalues, proxy)
  local ret
  local r1, r2, r3 -- one local per register the function uses
  while pos do
    -- a binary search. each leaf is one block.
    -- a block assigns pos, or sets pos = nil to halt.
  end
  pos = #proxy
  return unpack(ret)
end

A closure is not a nested container. It is a small wrapper that pins the upvalue id list and then calls this same container with a different starting position:

local function makeClosure(startPos, upvalueIds)
  local proxy = pin(upvalueIds)
  return function(...)
    return container(startPos, {...}, upvalueIds, proxy)
  end
end

The outermost call is wrapped again, once per Wrap-in-Function iteration:

return (function(...)
  -- encrypted strings, constant array, anti-tamper, then the vm
end)(...)

Peel those wrappers from the outside. They have no registers and no position. The first while pos you reach is the machine.

The host values handed to that machine are stable, and they are the first thing to name, because every later call is an index into this list: select, the vararg table, getfenv or _ENV, getmetatable, newproxy, unpack, setmetatable. Anything that is not one of those, and is not a register, is data.

Blocks, and how to cut them out

The body of while pos is not a list of instructions. It is a search tree. Four blocks or fewer become an if / elseif / else chain. More than that is split in half at the midpoint of two adjacent block ids, and each half is built the same way. The comparison is chosen from three equivalents, so you cannot match on the operator:

-- all three select the low half of the id range
pos < bound
bound > pos
-- or the high half, with the arms swapped
pos > bound

bound = floor((leftId + rightId) / 2). It is never an exact id compare.

A leaf of that tree is one block: straight-line assignments that end by writing pos. Block ids are sparse. The search exists so the interpreter never needs a table keyed by id. For recovery you do want that table. Walk the tree, and at every leaf record the id the leaf corresponds to. The id is the number that some other block writes into pos in order to arrive here. After the walk, dispatch is gone and you have a graph.

-- one block, after the search is removed
r1 = r2[r3]
r4 = r1 + 1
pos = (r4 and 18421) or 902

The terminator is the last write of pos in the block. Everything before it is the body. There are only a few terminator shapes, and every control structure Prometheus has is one of them:

TerminatorMeaning
pos = NUnconditional jump to block N
pos = (cond and A) or BIf cond then A else B
pos = nilHalt. The return table was written just above this.

Inside a block, statements that do not conflict on reads and writes may have been swapped, and several assignments may have been merged. Split a merged assignment back into singles when the targets are independent. Leave a swap alone: a, b = b, a was merged because the reads and writes overlap, and splitting it naively changes the meaning.

Conditionals

An if is not a Lua conditional. It is one terminator, and each arm ends by jumping to the join.

-- source
if reward then
  coins = coins + reward * multiplier
else
  coins = coins + 0
end

-- the test block. reward was copied into r2 before r1 was overwritten.
r1 = r2
pos = (r1 and 40) or 41

-- block 40
r3 = r3 + r2 * r4
pos = 42

-- block 41
pos = 42

-- block 42 is the join

The register that holds the condition is usually the same register that held the value being tested. The compiler evaluates the condition, then overwrites that register with a block id. A copy is taken first. If you substitute "whatever was assigned to this register last" without noticing the copy, the recovered test is if rewards[reward] when the source tested reward. The copy is the predicate. The block id is not a value.

and and or in the original expression are compiled the same way, as their own position updates, because they short-circuit. After the graph exists, a block whose only job is pos = (lhs and B) or A is the expansion of lhs or rhs or lhs and rhs. Fold it back into an expression when both arms are straight and write the same register. Do not fold it when one arm has a call. Short-circuit used to skip that call, and inlining it runs the call on both sides.

An if-expression (cond and a or b used as a value) saves the old position, runs the same encoding, and copies the position back afterwards. If a block stashes pos into a temporary and restores it at the end, you are inside an expression, not a statement. The value is whatever register the two arms agree on.

While, repeat, and both kinds of for

While

A while is a check block that the body jumps back to. The header is unconditional into the check. The check uses the same terminator as an if. The body ends with pos = check.

pos = CHECK
::CHECK::
pos = (cond and BODY) or EXIT
::BODY::
-- body
pos = CHECK
::EXIT::

A break is pos = EXIT. A continue is pos = CHECK. Once you have marked the header and the exit, both of those are ordinary statements again, and they are how you know a region is a loop rather than a nest of ifs that happens to jump around.

Repeat

Repeat enters the body first. The condition sits at the bottom, and the sense of the test is flipped: true means leave, false means go around again.

pos = BODY
::BODY::
-- body, which may itself jump
pos = (cond and EXIT) or BODY

Locals declared in the repeat body are cleared on the way out, either by writing nil or by calling the free-upvalue function. That clear is compiler output. It is not part of the source. Drop it when you emit repeat ... until cond.

Numeric for

This is the pattern that survives every other pass and still looks like an unreadable loop. Prometheus never emits for i = a, b, c. It emits a check block, and it initializes the counter to start - step so that the first trip through the check lands on start.

-- prologue, in the block that jumps to the check
limit = 10
step = 1
neg = step < 0          -- operands and the operator are shuffled
i = start - step       -- 0 when start and step are both 1
pos = CHECK

::CHECK::
i = step + i           -- or i + step. same shuffle.
pos = ((neg and i >= limit) or ((not neg) and i <= limit)) and BODY or EXIT

::BODY::
-- i is the loop variable. the body must not assign i.
pos = CHECK

The relational tests are built in pieces, into temporaries, and either operand may stand on the left. Normalize limit >= i to i <= limit before you try to read the direction. The boolean neg is computed once, from a comparison of the step against zero, and that comparison is also shuffled (step < 0 or 0 > step).

The step and the limit are registers. Those registers were used for something else earlier in the prologue block. The value in force at the loop is the last store before the check, not the first. If that last store is a constant, the loop is for i = start, limit, step, and a step of 1 can be omitted. If the body writes the counter, or something after EXIT still reads it, it is not a for-variable and the loop has to stay a while.

A concrete reduction:

-- prologue stores, last write wins
limit = 10
step  = 1
neg   = false
i     = 0          -- 1 - 1

-- reduces to
for i = 1, 10 do
  -- body
end

Generic for

A generic for keeps the three loop internals in registers: the iterator function, the invariant state, and the control variable. The check block calls the iterator and uses the first result both as the new control variable and as the condition.

pos = CHECK
::CHECK::
ctrl, v2 = iter(state, ctrl)
pos = (ctrl and BODY) or EXIT
::BODY::
v1 = ctrl
-- further results that the source did not bind are set to nil
pos = CHECK

That is for v1, v2 in iter, state, ctrl do. The iterator call is a multi-assignment on purpose. Do not split it. pairs and ipairs arrive here as ordinary calls; nothing in the VM marks them as special. If the iterator expression was pairs(t), you will see that call in the prologue, and its three results stored into iter, state, and ctrl.

Returns and calls

A return packs every result into a table, stores that table in the return register, and sets pos = nil. A tail call, or a returned vararg, is packed with unpack so the multiple results survive the table.

ret = { r1, r2 }
pos = nil

-- return f(x)  becomes
ret = { unpack(f(x)) }
pos = nil

The container then does return unpack(ret). So a recovered return r1, r2 is just the fields of that table, in order. An empty table is a bare return, which the compiler also inserts when a function falls off the end.

Arguments travel in args, not in registers, until the entry block copies them:

r1 = args[1]
r2 = args[2]
-- a vararg parameter becomes
r3 = { select(i, unpack(args)) }

A call in the middle of a block is an ordinary call. Method calls are compiled as a function call with the object passed explicitly, so player:WaitForChild("PlayerGui") comes back as a call of the function that was loaded from player.WaitForChild, with player as the first argument. You can print that with a colon again. Do not rewrite every index into a method call. An index may be a metamethod, and obj["m"](obj, x) is the form that still means the same thing if it is.

Numbers and the constant array

Numbers to Expressions runs before the VM, and sometimes on literals the VM itself emits. A literal becomes one of a few invertible trees: a sum of two random pieces, a product, a negation, a modulo identity. The modulo form is the one that looks nothing like the original number:

-- n, with a random rhs and a random multiplier k
(n + k * rhs) % rhs     -- equals n, for rhs > n in the generator's construction

Fold bottom-up, on integers, with the language's actual division. Prometheus uses Lua numbers. An integer-valued float is still a float in the source sometimes (531.0), and folding / or ^ through integers as if they were exact will invent a different constant. Fold +, -, *, % on integers exactly. Leave a division alone unless both sides are constants and you evaluate it as a float.

Constant Array lifts literals into one table at the top of the script, optionally rotates that table, and replaces each use with an index. Local wrapper functions add a fixed offset so the index in the wrapper is not the index in the array. The undo is mechanical, and it has to happen before you try to read string decryption seeds, because a seed is often one of those constants:

-- rotate left by R, undone by reading at (i + R - 1) % n + 1
-- a wrapper with offset K
local function wrap(i)
  return constants[i + K]
end

Find the rotation by looking for the loop that moves elements from the end of the array back to the front, or the other way. Find K by looking at the wrapper body, not at its name. Then inline wrap(i) to the literal. After that, a decrypt call has a numeric seed again instead of constants[wrap(i)].

The string cipher

Encrypt Strings replaces each string with a call that looks like it decrypts, and a table that looks like it holds the results. The function returns the seed. It does not return the string.

function DECRYPT(str, seed)
  if cache[seed] then
    return seed
  end
  -- write the plaintext into cache[seed], then:
  return seed
end

-- every use site is an index, and the index is the seed
STRINGS[DECRYPT(cipher, seed)]

STRINGS is a proxy. Its __index is cache, and its metatable is locked with __metatable = nil. The call exists only to fill the cache. The value the program wanted is the result of the index.

The character table is filled in random order and is still the identity:

for i = 1, 256 do
  nums[i] = i
end
repeat
  local n = table.remove(nums, math.random(1, #nums))
  charmap[n] = string.char(n - 1)
until #nums == 0

-- so charmap[b + 1] == string.char(b)

The generator is a 45-bit linear congruential step combined with a multiplier modulo 257. You can recognise a routine that has not been removed by the modulus 35184372088832. Seeding and one output byte look like this:

state45 = seed % 35184372088832
state8  = seed % 255 + 2

state45 = (state45 * mul45 + add45) % 35184372088832
repeat
  state8 = state8 * mul8 % 257
until state8 ~= 1

-- 32-bit mix of state45, rotated by (state8 % 32),
-- then split into four bytes and consumed from the end.

The multipliers and the initial previous-byte are constants in the decrypt closure, not in the call. Read them from the closure. Then each plaintext byte is:

prev = (cipherByte + nextByte() + prev) % 256
out  = out .. string.char(prev)

Run that once per call site and replace STRINGS[DECRYPT(cipher, seed)] with the literal. Replace a bare DECRYPT(cipher, seed) only when the next use of the result is an index into the cache. The function really does return the seed, and some surrounding code may use that seed as a seed.

Two traps. The tamper probe calls a similar-looking function with four arguments, not two. Leave those alone until the tamper section. And the decrypt closure is duplicated into other functions. A call inside a nested function is still a cipher until you run the same replacement there. If you delete the decrypt runtime first, those calls become calls of nil.

Upvalues, proxies, and refcounts

A local that is captured does not stay a local. It becomes a slot in one environment table. The slot id is allocated by a function that is easy to mistake for junk:

local function alloc()
  nextId = nextId + 1
  refcount[nextId] = 1
  return nextId
end

The store of 1 is the initialization. A later incref does refcount[id] = refcount[id] + 1. If you delete alloc because the returned id looks unused, the incref reads nil and the script dies on nil + 1. The matching free walks a list of ids, subtracts one, and nils both the refcount and the value at zero:

local function free(ids)
  local i, id = 1, ids[1]
  while id do
    refcount[id] = refcount[id] - 1
    if refcount[id] == 0 then
      refcount[id], values[id] = nil, nil
    end
    i = i + 1
    id = ids[i]
  end
end

Closures do not hold the values. They hold a proxy whose __index is the list of slot ids, whose __gc is free, and whose __len returns a random constant chosen once per compile. That length is the #proxy you saw after the interpreter loop. On Lua builds without newproxy, the same object is a table with the same three metamethods. Either way, a captured read in the VM is values[upvalues[k]].

To put a name back on it, find the store that filled the slot, and snapshot the value at that store. The register used for the store will be reused. The slot will not, until something writes the slot again.

values[slot] = stats
-- the register "stats" is about to be overwritten with the next temporary.
-- the slot still holds the table.
local cap = stats

-- a later read values[upvalues[k]], where upvalues[k] == slot,
-- is a read of cap. writes through cap are writes through the table.

If a later instruction stores a different object into the same slot, the snapshot is wrong and the read has to stay an environment read. If two closures capture the same store, they share one snapshot local.

Registers are also reused across nested functions in the lifted text even when they are not upvalues. An inner function that assigns a register without reading it first needs its own local. An inner function whose first mention of the name is a read (count = count + 1) is writing the outer variable and must not be given a shadowing local. That distinction is the whole difference between a callback that updates a counter and a callback that updates a dead temporary.

Anti-tamper

The tamper pass is a block of Lua inserted around the program, not a VM opcode. It fails closed into an infinite loop. Removing it badly is worse than leaving it, because the failure path does not return.

The checks, in the order they matter:

  1. debug.getinfo must still report that pcall, string.char, debug.getinfo, and string.dump are C functions. A hook that replaces any of them with a Lua function fails here.
  2. A pcall of an empty function must succeed, and the flag set inside that function must be visible afterwards. A pcall that returns true without running the function fails here.
  3. Two copies of the same crashing expression are evaluated. The expression is a number minus a string raised to a number, used as a divisor. Lua's error text contains :line:. Both copies must report the same line.
  4. A loop of random length either re-raises a rewritten error or builds a byte array and returns it with unpack. The sum of the returned bytes has to match the sum of the bytes that were written. This loop calls math.random. It is not user code.

The line check is the one that breaks formatters. Both probes have to be the same syntactic line, because the test is equality of the two captured line numbers, not equality to a constant. If you pretty-print one probe onto its own line, they differ, valid becomes false, and you take the failure path.

The failure path is approximately:

repeat
  return (function()
    while true do
      l1, l2 = l2, l1
      error("Tamper Detected!")
    end
  end)()
until true
while true do
  -- a second loop, also endless
end

If you replace error with a function that returns, the first loop never exits. The script does not skip the check. It spins. The second loop is unreachable only because of the return of that spinning call. So the whole if valid then else ... end has to be deleted as a unit, probes included, or both probes have to stay on one shared helper so they report one line and valid stays true. A stub that swallows error is not a deobfuscation.

After the block is gone, ignore the math.random calls that lived inside it. They exist to make the byte-sum check and to disturb anyone diffing RNG state. A script that did not itself call math.random still prints the same results once those calls are gone. Compare the prints and the return values, not the generator.

A recovery procedure

The passes undo in roughly the reverse of the order they were applied. Doing it in another order either deletes the program along with the interpreter, or keeps the interpreter because a cipher call still looks live.

  1. Unwrap. Strip return (function(...) ... end)(...) until the body is no longer only a wrapper. Name the seven host parameters.
  2. Fold numbers and the constant array. You want numeric block ids and numeric seeds before you trust any comparison or any decrypt call.
  3. Find the container. It is the function whose body is while pos do ... end followed by pos = #proxy and return unpack(ret). Every other function that ends by calling it is a closure wrapper.
  4. Cut the search tree into blocks. Walk the comparisons. A leaf is a block. The terminator is the last write of pos. Build the graph: unconditional edge, two-way edge, or halt.
  5. Decrypt strings. In every function that contains the 45-bit modulus, read mul45, add45, mul8, and the initial previous-byte. Replace STRINGS[DECRYPT(s, seed)] with the plaintext. Do this inside nested functions before you ask which calls are still needed.
  6. Delete the tamper block by the rules above, not by no-op'ing error.
  7. Structure the graph per function, starting from the block that the container is entered at for that function. The entry of a closure is the constant passed as startPos.
  8. Bind upvalues by snapshotting the environment store that feeds each captured slot.
  9. Remove the runtime only after nothing in the structured program still indexes the value table, the refcount table, or the proxy. Alloc and free go together. An alloc whose id is unused is not dead if a later incref reads that id.
  10. Rename registers last. Until then their identity is how you track reaching definitions. A register's reaching store is the last write on every path that can arrive at the use without another write. Compute that once per statement. Recomputing it from the top of the block on every use is quadratic in the size of the block, and a large function is one block until you split it.

Reaching definitions are the whole analysis. A terminator pos = (r1 and A) or B is only an if on reward if the store that reached r1 is the copy of reward, not an earlier store into the same register and not the block id that this very statement writes. Same for the for-loop step: the store that reaches the add is the last one in the prologue, even if that register held a table twenty lines earlier.

A compact way to keep it:

-- before each statement, map each register to the set of stores that reach it
reach = merge(predecessors)
for stmt in block do
  stmt.reach = reach
  for reg in writes(stmt) do
    reach = copy(reach)
    reach[reg] = { stmt }
  end
end

The merge at the top of a block is what makes loops correct. A register written in the body and read in the header has both the prologue store and the body store until you notice the body store kills it. That is also how you prove the for-variable is not used after the loop: from the exit block, walk forward, and stop at the first write.

Structuring, and when to stop

With the graph in hand, structuring is ordinary. A header whose body can reach the header again, and whose other edge leaves, is a loop. If the header matches the numeric-for check, emit a for. If the condition is at the bottom and the back-edge is the false arm, emit a repeat. Otherwise emit a while. Two arms that both reach a block neither of them contains are an if, and that block is the join. Emit the conditional and continue from the join.

function structure(block, stop)
  while block and not stop[block] do
    if isForHeader(block) then
      emitFor(block)
      block = block.exit
    elseif isWhileHeader(block) then
      emitWhile(block)
      block = block.exit
    elseif block.kind == "if" then
      join = findJoin(block.then, block.else_, stop)
      if not join then
        break -- do not invent one
      end
      emitIf(block, structure(block.then, join), structure(block.else_, join))
      block = join
    else
      emit(block.body)
      block = block.next
    end
  end
end

findJoin is the first block reachable from both arms, excluding the header you are already inside. If it returns nothing, the arms do not meet. Falling back to "emit both arms anyway" duplicates every block they share further down. On a small function whose arms really do not meet, such as a decrypt routine where the cache hit returns and the miss falls into a byte loop, that duplication does not happen and the result looks right. On a large function the arms share a tail that the join test missed because of a back-edge, both copies get emitted, and a back-edge turned into a goto lands on the copy you just wrote. The goto targets itself. The function no longer terminates. Programs that used to return a number start spinning, and the structured text is a different program, not a decompilation.

When a region will not reduce, print the blocks and the terminators. A leftover goto is a true edge. A synthesized loop that was not in the graph is not. Nested functions are separate graphs with their own entry positions. One function that will not reduce does not license you to leave the interpreter wrapped around the functions that will. Clean what structured. Leave the rest as a graph.

After a function has no remaining jumps, the environment table, the refcount table, and the proxy are dead weight, and the stores into them can go. While a jump remains, a store that looks unused on one path may be the value another path returns. Deleting it is how a function that should return an updated counter starts returning nil.

What you have at the end is the original control flow, the original constants, and the original calls, with registers instead of names. The names were never in the file. Choosing v1, v2, v3 in one sequence for the whole script, rather than restarting in every function, is enough to read it. Inventing the old names is a guess, and a wrong guess is a worse artifact than a numbered local.
